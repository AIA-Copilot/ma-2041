# Day 1 · Lab 2 — Connect Il Ristorante to its API

**Workspace:** use VS Code and PowerShell 7 inside the provided MS-4018 VM. “Local” means this VM. One-time preparation: [course setup](../README.md).


**Outcome:** Copilot retrieves a menu from your running local TypeScript Azure Functions API through a dev tunnel, then submits a confirmed simulated order. You will connect an OpenAPI document, an API-plugin manifest, and a declarative-agent manifest.

**Allow:** 45 minutes of practice after provider preflight (planning budget, not measured completion). Complete the account, custom-app upload and anonymous-tunnel gates in the [Day1 README](../Day1/README.md). The API is a fictitious restaurant. No payments or real orders exist; the order ID is generated by the sample. This is not production authentication or restaurant fulfillment.

**Start gate:** the instructor must confirm [provider preflight](INSTRUCTOR-PREFLIGHT.md) before runtime work. If tools or approval are missing, stop; do not install or bypass policy during this lab.

**Official exercise:** [Create a declarative agent with an API plugin](https://learn.microsoft.com/en-us/training/modules/copilot-declarative-agent-action-api-plugin-vsc/3-exercise-create-declarative-agent-api-plugin). This project retains the official TypeScript starter, dataset, icons and license. Prepared checkpoints let you recover from editing errors without fabricating tenant success.

## 2. Trace the API contract and implementation (5 minutes)

1. Open these files side by side and locate each item in the table:

| File | What to identify |
|---|---|
| `appPackage/apiSpecificationFile/ristorante.yml` | `servers`, `GET /dishes`, `POST /orders`, and unique `operationId` values `getDishes` and `placeOrder` |
| `src/data.json` | Menu names, course, type, allergens, price and image URL |
| `src/functions/dishes.ts` | Query filters and `{ "dishes": [...] }` response shape |
| `src/functions/placeOrder.ts` | Input validation, name matching, total calculation, simulated confirmation |

The source dataset is `src/data.json`; the import `../data.json` is relative to the functions folder. No database is required. The menu filter **excludes** dishes containing requested allergens. OpenAPI declares `style: form` and `explode: false`: send one comma-separated value, for example `?allergens=dairy,gluten`, not repeated `allergens` keys. The handler reads one query value and splits it on commas. `POST /orders` is plural: `app.http("orders", ...)` supplies the route because no explicit route overrides it. The function name `placeOrder` is not the URL. This is demonstration data, not medical/allergy advice.

The API accepts names rather than numeric menu IDs so Copilot can use dish names in the request. The contract and handler both require integer quantities **1–100 inclusive**; empty/malformed orders, fractional quantities, zero, negatives and values above 100 are rejected before totals are calculated. It does not turn this toy API into a secure production service.

**Checkpoint:** Trace each operation ID to its handler and response shape.

## 3. Test the real local HTTP host before introducing Copilot (7 minutes)

1. Create the no-secret local Functions settings and start the host in the project terminal:

```powershell
'{"IsEncrypted":false,"Values":{"FUNCTIONS_WORKER_RUNTIME":"node"}}' | Set-Content local.settings.json -Encoding ascii
npm.cmd start
```

2. Wait until the Functions host lists `/api/dishes` and `/api/orders`. This starts a local process only; it does not create a tunnel or tenant app. Leave it running and open a second PowerShell terminal in the same folder:

```powershell
Invoke-RestMethod 'http://localhost:7071/api/dishes?course=lunch'
Invoke-RestMethod 'http://localhost:7071/api/dishes?course=lunch&allergens=dairy,gluten'
$body = @{ dishes = @(@{name='spaghetti';quantity=1}, @{name='iced tea';quantity=1}) } | ConvertTo-Json -Depth 5
Invoke-RestMethod 'http://localhost:7071/api/orders' -Method Post -ContentType 'application/json' -Body $body
```

**Expected result:** each menu response is an object with a `dishes` array (possibly empty), not a top-level array. The second query excludes both dairy and gluten. Then expect a response with `order_id`, `status: confirmed` and a positive `total_price`. The order ID varies. Compare the total to the matching menu entries; do not expect a copied screenshot's ID.

3. Run the negative test:

```powershell
try {
  Invoke-RestMethod 'http://localhost:7071/api/orders' -Method Post -ContentType 'application/json' -Body '{"dishes":[{"name":"spaghetti","quantity":-1}]}'
} catch {
  $_.Exception.Response.StatusCode.value__
}
```

Expected HTTP **400**. Repeat with quantity `101`, then `1.5`; both must return 400. Restore the valid `$body` request above (quantity `1`) and verify 201 again. If an invalid order succeeds, inspect whether you are running a stale host or different project. Return to the host terminal and press Ctrl+C. Stop it before F5; otherwise Toolkit's port check should correctly refuse to start another host.

**Checkpoint:** Record real HTTP success and all three invalid-quantity failures.

## 4. Apply and inspect the supplied plugin checkpoint (7 minutes)

The official exercise creates `appPackage/ai-plugin.json`, declares functions/runtimes, then references that plugin from the agent. This folder begins with the starter agent so that connection is explicit.

1. Open `checkpoints/ai-plugin.json`. Check these fields before copying:

- `run_for_functions` includes `getDishes` and `placeOrder`.

The agent is **Il Ristorante** and includes menu/dietary conversation starters. Read `instruction.txt`; it describes the restaurant scope and order payload. ## 5. Understand the cloud-to-local bridge (3 minutes)

1. Open `appPackage/apiSpecificationFile/ristorante.yml` and find the prepared server token:

```yaml
servers:
  - url: ${{OPENAPI_SERVER_URL}}/api
    description: Il Ristorante API server
```

2. Open `.vscode/tasks.json`, **Start local tunnel**. It publishes port 7071 with `access: public` and writes `OPENAPI_SERVER_URL`. The literal `${{...}}` is replaced by Toolkit when building the app package. **Do not replace it with localhost**: cloud Copilot cannot reach the localhost address inside your VM.

The local F5 task sequence checks prerequisites, starts the tunnel, provisions the Microsoft 365 app, installs/builds the backend, and starts the host/debugger. `m365agents.local.yml` has the local lifecycle. The main lifecycle intentionally contains no Azure resource deployment.

**Safety stop:** confirm the instructor permits this anonymous tunnel and that port 7071 serves only the supplied fictitious API. Do not tunnel the connector, another service, or private data.

**Checkpoint:** Explain how the approved HTTPS tunnel replaces the server token.

## 6. Start the local debugging path and test in Copilot (15 minutes)

1. In Toolkit > **Accounts**, verify your assigned work account.
2. In **Run and Debug**, choose **Debug in Copilot (Edge)**, not **Preview in Copilot**. Press F5.
3. Review Toolkit output and terminal tasks. Sign in to the approved dev-tunnel provider if prompted. Do not authorize an unexpected tenant or service.
4. Wait for local provisioning/build/start to complete. The browser opens Microsoft 365 Copilot. Sign in to the same account and select **Il Ristorante** in the Agents/side panel.
5. Inspect the generated app package's OpenAPI file under `appPackage/build`: its server should contain a real HTTPS tunnel endpoint ending in `/api`, not an unresolved variable or localhost. Do not share the full generated environment files.

Submit the conversation starter:

```text
What's for lunch today?
```

When Copilot asks permission, inspect the request. For a read, use **Allow once** only if it is the expected menu API and contains no private information. Wait for the answer. Open a dish citation: at this stage it has the title/basic response, **not** your custom Adaptive Card.

Submit:

```text
1x spaghetti, 1x iced tea
```

Inspect the proposed order data before choosing **Confirm**. Confirm only the expected fictitious dishes and quantities. The reply should include a simulated confirmation and total matching the backend response. Correlate the time of the request with your Functions terminal; a plausible answer without an API call is not enough.

Try an unsupported menu request:

```text
Order one item called nonexistent dish.
```

The agent should seek clarification or report it cannot place that order; it must not invent a successful fulfillment. If it proposes an unexpected payload, cancel it. The deterministic HTTP negative test earlier separately proves the backend rejects invalid data even if model behavior varies.

**Checkpoint:** Record menu read, confirmed simulated order and unsupported-item behavior.

## Recovery table

| Symptom | Correct next action |
|---|---|
| Port occupied | Stop the earlier local host/Lab 2 or 3 debugging session. Do not change one port without changing all task/OpenAPI references. |
| F5 opens Copilot but no API starts | You may have chosen Preview instead of Debug. Stop, select Debug in Copilot (Edge), retry. |
| Tunnel denied or blocked | Instructor/network policy gate. Keep the local HTTP evidence, mark cloud action blocked; do not bypass tenant or firewall policy. |
| API returns 404 from Copilot | Check generated HTTPS server includes `/api`, host routes are running, and tunnel matches this run. |
| Plugin/function not found | Compare `actions.file`, `spec.url`, function names and OpenAPI operation IDs; reapply the checkpoint only if needed. |
| Updated code but old action behavior | Save, stop all tasks, rerun F5 to rebuild/provision and start a fresh agent chat. |
| App upload/consent denied | Capture the exact failing stage; ask the tenant admin. Do not select a random other account. |
